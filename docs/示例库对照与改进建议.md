## 一、示例库到底有什么

先纠正一个预期：**这是一个「一页一 demo」教学仓库，不是完整产品**。
全仓库仅 **3 个示例页 + 1 个共享层**，代码总量约 3000 行（不含依赖）。

| 示例 | 体量 | 定位 | 依赖接口版本 |
|---|---|---|---|
| `PublicCloud/DeviceList` | main.ts 84KB + DevicePanel.ts 28KB | 设备列表 + 物模型详情 + HMS 抽屉 | **v2.0** |
| `Privatization/DeviceList` | main.ts 69KB + DevicePanel.ts 28KB | 同上（私有化，数字枚举） | v1.0/v2.0 |
| `Privatization/FlightTaskLibrary` | main.ts 35KB | 飞行任务全生命周期（列表 + 新建） | v2.0 |
| `Shared/request.ts` + `types.ts` | 4KB | fetch 封装（注入 `x-user-token` / `X-Project-Uuid`） | — |

**它完全没有覆盖**：地图可视化、图传/直播、飞行控制、一键起飞、实时遥测 HUD。
这些恰好是我们平台的重头，所以本次对照是「互补」而非「替代」。

示例库的三个技术取向值得注意：

1. **接口版本用 v2.0**：`/openapi/v2.0/project/device`、`/openapi/v2.0/device/{sn}/state`、
   `/openapi/v2.0/device/hms`、`/openapi/v2.0/task/api/v2/workspaces/{projId}/flight-tasks`。
   我们平台目前统一走 **v0.1**（`server/src/djiClient.js` 的 `PREFIX`）。
2. **不做中间层**：浏览器直连司空 2，靠 Vite 反代绕跨域。我们走了 BFF，多一层但换来
   统一鉴权/缓存/日志/跨域零配置。
3. **以「字段映射表」为交付重点**：每个示例的 README 里都有几百行字段路径表，
   这部分是本次最有价值的可搬运资产。

### 缺口 2 · 地面站（base_station）与中继站（relay）完全没有支持

**现状**：`server/src/modules/drone/services/telemetry.js` 的 `flatten()` **只读
`item.gateway` 和 `item.drone`**，设备树里其它类型的设备被直接丢弃。
前端 `store` 也只有 `airports` / `drones` 两个数组。

**示例库**：`ManageDevice` 接口里除了 `associate_drone_device_info`，还有
`associate_relay_device_info` / `associate_dock_device_info`，并且
`AIRPORT_LIKE_CLASSES = ['airport','base_station','dock','hangar']` 统一归类；
`RELAY_WORKING_MAP` 单独一套（0 已连接 / 14 未连接 / 65535 状态异常）。

**建议**：`flatten()` 增加 `baseStations` / `relays` 通道（按 `device_model.class` 或
`device_model.key` 前缀 `6-`/`8-`/`9-` 判定），前端设备管理页加 tab 区分。
这项工作在有多地面站的现场会直接暴露为「设备列表少一半」。

### 缺口 3 · 飞行任务列表（这是被我们自己删掉的）

**现状**：`taskApi.list` 只在首页大屏用来数 KPI；`taskApi.media(uuid)` **全项目零调用**；
没有任何地方把 `task_status` 翻译成人话（grep「待执行/执行中/task_status」全库 0 命中）。
可用的数据其实都在，只是没渲染。

**示例库的做法**：

- **Tab**：`[未完成]` / `[已结束]`（`flight_task_status = 1 / 2`）
- **8 列表格**：计划|实际时间 / 执行状态 / 类型 / 计划名称 / 航线名称 / 设备名称 / 创建人 / 媒体上传
- **按日期分组**渲染
- **执行状态归并**（原始 11 态 → 4 类显示，颜色：待执行蓝 / 执行中绿 / 执行成功绿 / 执行失败红）：

  | 显示 | 颜色 | 原始 `task_status` |
  |---|---|---|
  | 待执行 | 蓝 | 0 / 6 / 9 / 10 |
  | 执行中 | 绿 | 2 / 3 |
  | 执行成功 | 绿 | 5 |
  | 执行失败 | 红 | 1 / 4 / 7 / 8 |

- **类型映射**：`flight_task_type` 1 自动 / 2 手动
- **设备多选筛选**：选中 SN 数组作为 `sn[]` 查询参数，含「全选在线设备」
- **30s 轮询**刷新状态、航点进度、异常、媒体上传进度

**建议**：不必恢复成独立一级菜单（用户此前明确要求删掉），但应该在
**航线管理页**里加一个「执行记录」抽屉/二级 tab，复用 `taskApi.list` +
`taskApi.media`，套用上面的状态映射。这样既回应了「删掉冗余栏」的诉求，
又补回了「任务跑了没有、素材传完没有」这个真实运维问题。

**落点**：`web/src/views/WaylineView.vue` + `web/src/utils/dict.js`（加 `TASK_STATUS_MAP`）。

### 缺口 4 · HMS 只剩一层，丢了根因与时间

**现状**：`CockpitView.vue` 的 HMS 面板已按等级配色并排序（本次刚加），
但仍缺 **根因展开** 与 **起止时间**。

**示例库字段**：`hms_id`、`level`、`module`、`in_the_sky`、`imminent`、`status_key`、
`code`、`message`、`begin_time`、`end_time`、**`sub_hms_list`（根因树）**、`domain_type`，
并标记 `_isRootCause` 做「根因 HMS 展开收起」。

**建议**：`loadHms` 保留 `sub_hms_list`，HMS 面板每条可展开显示子告警 +
起止时间；`imminent === true` 的用告警色加粗（表示即将发生）。

### 缺口 5 · 中英文切换（i18n）

**现状**：全站硬编码中文。

**示例库**：内置 `messages = { zh, en }` 两套字典，右上角一键切换，
选择存 `localStorage`，**无第三方 i18n 依赖**。

**建议**：如果产品有对外/海外交付可能，值得补；否则优先级最低。
若做，按示例库的轻量方案（一个 `dict.js` + `store.lang`）即可，不必上 vue-i18n。

---

### 缺口 6 · 公有云 v2.0 字符串枚举适配

**现状**：`djiClient.js` 里 `PREFIX = '/openapi/v0.1'` 写死，全平台按**数字枚举**解析。

**示例库**：公有云 v2.0 返回的是**字符串枚举**（`mode_code='idle'`、
`rainfall='light_rain'`、`device_online_status='power_on'`、
`drone_in_dock='inside'`、`is_calibration='calibrated'`），
因此专门写了 `adaptPublicCloudState()`（200 行）把字符串统一转成数字/布尔，
其中 `PUBLIC_MODE_CODE_MAP` 覆盖了机场/飞行器两套字符串枚举。

**建议**：
- 短期：不必迁移。我们的 v0.1 + 数字枚举目前工作正常。
- 中期：把 v2.0 适配表（`adaptPublicCloudState` 的各张 map）**预先收进
  `web/src/utils/dict.js`**，并让 `modeText()` 同时接受字符串与数字。
  一旦司空 2 停止维护 v0.1，改动面就只是 `PREFIX` 一处。
- 注意：v2.0 还有 `device_working_status` 字段（我们用的 `mode_code` 是 v0.1 的叫法）。

### 缺口 7 · 轮询状态可见性（小改进）

**现状**：座舱有 10s `refreshStates` 定时器，但**界面上看不出「在轮询 / 已停止」**，
出问题时用户不知道是数据没刷还是界面卡了。

**示例库**：顶部状态条显式显示绿色「轮询中 (30s)」/ 灰色「已停止」。

**建议**：顶栏加一个小圆点 + 文案，`store` 暴露 `pollingState`。
改动量 10 行，但显著降低「是不是坏了」的沟通成本。

### 缺口 8 · 一些低成本细节

| 项 | 示例库做法 | 建议 |

## 四、我们比示例库强的地方（保持，不要为了对齐而削弱）

1. **BFF 架构**：示例库浏览器直连司空 2，必须靠 Vite 反代才能绕跨域；
   我们单端口 8787 同时托管 API + 静态资源，鉴权头/TK 多组织/缓存/日志全在服务端统一处理。
   → 示例库的 `Shared/request.ts` 思路我们已经实现得更好，无需改动。
2. **图传直播**：示例库**完全没有**。我们已打通 volc RTC 播放 + 自动开机链路。
3. **地图与空间认知**：Leaflet 底图、设备标记、机巢切换，示例库没有。
4. **飞行控制闭环**：预检 → 一键起飞 → 步骤进度 → 状态轮询。
5. **容错与可诊断性**：错误码中文释义、实时日志、API 测试器、HUD 降级提示。
   示例库是教学代码，几乎不做容错。

## 八、相机范式化改造（按设备类型，不按设备特化）

### 背景：一个被错误判据掩盖的真 bug

用户反馈「职校机场直播没画面」。排查初期用「`videoWidth > 0` 且 `currentTime` 推进」判定成功，
两台机场**都判定为正常播放**，于是得出错误结论「舱外相机没装、切过去不推流」，
并把舱外机位当死选项删掉了 —— bug 依然存在。

真实原因：**「有流」不等于「有画面」**。用 canvas 采样画面亮度后真相大白：

| 机场 | 机位 | 画面亮度（mean / std） | 结论 |
|---|---|---|---|
| 职校 | 舱内 indoor | **0 / 0** | 纯黑 |
| 职校 | 舱外 outdoor | 152 / 54 | 正常 |
| 深圳机场3 | 舱外 outdoor | 151 / 58 | 正常 |

职校的舱内相机输出的就是一路**纯黑流**，尺寸 1280×720、时间轴照常推进，
只靠「有没有流」永远查不出来。之前「舱外不推流」的结论是**误判，已推翻**。

### 结构性问题：不要按设备适配，要按「模块范式」适配

第一版修复打算「按机场 SN 记住上次成功机位」——这属于**设备特化**：
换一台同型号机场就要改代码，且上线后无法自愈。已弃用。

正确做法：**同型号（device_model.key 相同）设备走完全相同的代码路径**，
差异由「类型级范式 + 运行时实测回退」消化。

新增两个范式模块（前后端同源同义）：

- `server/src/modules/drone/services/cameraProfile.js`
- `web/src/utils/cameraProfile.js`

范式内容（按 `device_model.class` 定义，不含任何 SN 分支）：

| 类型 | 机位顺序 | 黑屏自动回退 | 兜底 camera_index |
|---|---|---|---|
| `airport`（Dock 3） | `outdoor → indoor` | 允许 | `165-0-7` |
| `drone`（Matrice 4TD） | 无（云台无舱内外） | 不允许 | `176-0-0` |

相机选择规则（机型无关）：按 `available_lens_types` 数量降序选主云台
（Matrice 4TD 取 `camera_list[0]` 会选中推不出流的那一路）。

### 成功的第 4 级判据

此前已有三级：① `/live-stream/start` 返回 code=0 ② RTC 订阅成功 ③ `videoWidth>0` 且时间轴推进。
现在补上第 4 级（也是唯一可信的）：**画面有内容** —— 亮度均值 ≥ 8 或标准差 ≥ 4。

`LivePlayer.vue` 每 1.5s 采样一次（160×90 缩放后统计灰度），连续 3 次判定为纯黑：

- 显示「画面为纯黑（相机无光照）」，角标改为「已接通 · 画面全黑」，**不再显示"直播中"骗人**
- 黑屏**不触发自动重连**（重连解决不了无光），而是按范式切下一机位
- 提供「切换机位」手动按钮

### 顺带修掉的真 bug

**换机场后画面串台**：两台 Dock 3 的 `camera_index` 完全相同（都是 `165-0-7`），
原 `watch(airportCameraIndex)` 在换机场时 `idx === prev`，监听根本不触发，
左侧一直播着上一台机场的流（表现为「切到深圳还是那个黑屏」）。
已改为 `watch([dockSn, airportCameraIndex])`。

### 范式化清理

删除硬编码：`liveService.js` 的 `FALLBACK_INDEX = '165-0-7'`、
`controlService.js` 的 `DRONE_FALLBACK_INDEX = '176-0-0'`，
统一收敛到 `cameraProfile.js` 的类型级 `fallbackIndex`。

### 验证

两台机场走同一套范式路径（舱外优先）均直接出画面：职校 150.4、深圳机场3 150.7。

回归 **95 通过 / 0 失败 / 1 告警**（原 92 项一个不少 + 新增 3 项：
机位按范式取舱外 / 画面有实际内容（亮度检测）/ 黑屏提示不误报）。

## 九、飞行记录与航拍照片（主线已跑通）

### 链路

```
flight-task/list?sn=<机场SN>&begin_at=&end_at=   →  任务列表
flight-task/{uuid}/media                          →  该任务的媒体清单（≤10000，含 preview/original url）
后端 /api/task/{uuid}/media/{mediaUuid}?type=preview|original  →  图片代理（签名 URL 不落前端）
```

### 三个坑

1. **`flight-task/list` 的 `sn` / `begin_at` / `end_at` 是必填，但缺参不报错** —— 只返回 `code=0` + 空列表，
   极其容易被误判成「这个机场没飞过」。后端已改为显式拒绝并说明原因。
2. **`sn` 必须传机场（网关）SN，传飞行器 SN 返回 0 行**。前端按设备列表把飞行器 SN 映射回所属机场 SN 再查。
3. **媒体 URL 带 `auth_key` 签名、CDN 直连、且每次调用都会重新签发** —— 不能缓存长期链接，
   必须由后端代理转发（预览走 `preview_url`，看原图走 `original_url`）。

### 已实现

- 执行记录抽屉：时间范围（7/30/90/365 天，默认 90）+ 多机场并行聚合 + 按 uuid 去重 + 时间倒序
- 表格新增「航拍照片」列：`upload_finished` 显示「查看照片」，`to_upload` 显示「未上传」（不是「没照片」）
- 照片墙抽屉：CSS Grid + `<img loading="lazy">`，每页 24 张，滚动到底/点击加载更多，点击看原图
- 后端媒体清单 5 分钟短缓存，避免每次翻页都打司空 2

### 实测

58 条飞行记录，44 条带照片；「实操考核」任务照片墙 24/24 张全部经代理加载成功。
截图：`docs/screenshot-flight-media-wall.png`。

### 待办（可选）

`flight-task/{uuid}/track` 拉轨迹点，在地图上画出该架次的飞行航迹。

## 十、航线下载与上传

### 现象

下载下来的航线文件选不中、传不上去。

### 真相

**上传其实是成功的**（返回了 uuid，列表里能查到，总数从 34 变 35）。
真正的原因是响应头只写了 `filename*=UTF-8''...`，没写 ASCII 兜底的 `filename=`，
部分浏览器因此丢掉扩展名，本地文件没有 `.kmz` 后缀，被 `<input accept=".kmz,.kml">` 直接过滤掉了。

### 处理

- `Content-Disposition` 双写：`filename="ascii.kmz"; filename*=UTF-8''%E4%B8%AD%E6%96%87.kmz`
- 文件名从司空 2 返回的 `name` 去尾缀后强制补 `.kmz`（DJI 的 `name` 不带扩展名）
- 上传控件的 `accept` 放宽到 `.kmz,.kml,.zip`，并在 JS 里校验后缀给出明确提示

### KMZ 是什么

KMZ 就是 ZIP，里面是 `wpmz/template.kml` + `wpmz/waylines.wpml`（DJI WPML 格式），
所以 `.zip` 后缀同样能上传，这正是「换个后缀就能传」的原因。

### 注意

司空 2 OpenAPI **没有删除航线的接口**，测试上传的航线只能在司空 2 界面里手动删。

### 顺带

Node 22 的 `fetch` 返回的是 Web ReadableStream，不能直接 `.pipe(res)`，
要用 `Readable.fromWeb(upstream.body).pipe(res)`（否则 502 + `body.pipe is not a function`）。

## 十一、照片墙 219021 报错的原因与处理

### 现象

执行记录里部分任务点了「查看照片」后，弹「服务器异常，请稍后重试」，抽屉显示 0 张照片。

### 根因

`flight-task/list` 会返回两类任务：

1. **正常航线任务**：用户创建的航线飞行，有真实航拍照片。
2. **机场自动动作记录**：`task_type === 'others'`，名字通常是 `FlyToTask_<机场SN>`，
   是机场自己生成的起飞/返航/降落动作，**没有航拍照片**。

但这类自动任务的 `media_upload_status` 也可能显示 `upload_finished`，
导致前端按「已上传」放行。实际调用 `/flight-task/{uuid}/media` 时，
司空 2 返回 **219021 服务器异常**，连 `/flight-task/{uuid}` 详情也会返回 `record not found`。

### 处理

- `isUploaded()` 增加过滤：`task_type === 'others'` 直接判为未上传，按钮显示「无照片」并置灰。
- 即使绕过按钮点进来，`openMedia()` 对 219021 给出专门提示：
  「司空 2 无法读取该任务媒体（多为机场自动产生的飞行动作记录，无航拍照片）。」

## 十九、三维模型预览：真 LOD + 坐标修正（修复「放大不清晰 / 坐标不对」）

### 根因（三个叠在一起）

1. **只渲染了一个分块。**
   模型包里其实有 3 个 `tileset.json`：

   ```
   Project1 2/B3DM/Model_0/tileset.json        ← 总根（boundingVolume 直接是 ECEF）
   Project1 2/B3DM/Model_0/BlockA/tileset.json ← 被引用的子块
   Project1 2/B3DM/Model_0/BlockX/tileset.json ← 被引用的子块
   ```

   总根的两个 child 用 `content.uri = "BlockA/tileset.json"` 引用子块（3D Tiles 的外部瓦片集）。
   旧代码用 `files.find(/tileset.*\.json$/)` 取**第一个**匹配，命中的是 `BlockA`，
   655 个 b3dm 里只渲染了 10 个 —— 看到的是残缺的一小块，视觉上就像「坐标错了」。

2. **子块 json 没展开。**
   `BlockA/tileset.json` 里还有 `BlockA_L16_2.json`、`BlockA_L17_7.json`、`BlockA_L18_17.json` 这类
   **层层嵌套的外部瓦片集**（包内共 30 个 json、655 个 b3dm）。旧代码只认文件名带 `tileset` 的 json，
   这些子块全部被跳过，所以永远停在 L13 这一层最粗的瓦片上 —— 这就是「放大也不变清晰」。

3. **Z-up 修正的顺序反了。**
   旧代码先对单个瓦片做 `rotateX(-90°)`，再乘 ECEF 的 `transform`。
   正确顺序是：瓦片内容（Z-up 局部坐标）→ 乘 ECEF transform → **整体**再转 Y-up。
   顺序反了模型姿态会歪。

### 修复

**后端 `server/src/routes/model.js`**

- 新增 `resolveTilesets()`：把包内所有 `tileset*.json` 读一遍，收集谁被别人当外部瓦片集引用
  （`collectExternalRefs`），没被引用的就是根。
- `/files` 返回新增 `tilesets`（全部）与 `tilesetRoots`（根）字段；
  老清单缺这两个字段时就地补算，不会重新下载模型包。

**前端 `web/src/components/ModelViewer.vue`**

- `expandTree()`：多轮展开。每轮把未拿到的外部 json 记进 `pendingTilesets`，下一轮并发补齐，
  最多 10 轮，直到没有新引用。子块 L16 → L18 → L19 的嵌套能全部展开。
- `buildTree()` 支持 `content.uri` 为 `.json` 的外部瓦片集，就地并入同一棵树。
- LOD 判据改用**屏幕投影像素**（`projectedPixels`）而不是 `geometricError`：
  司空 2 导出的 tileset 里 `geometricError` 大量是异常值 `1e10`，用它判据会「永远细化」或「永不细化」。
  `MAX_PIXELS = 220`：瓦片包围球投影直径超过 220px 就细化到子瓦片。
- **无自身内容的分组节点必须细化**（`mustRefine = hasChildren && !node.uri`），否则会出现空洞。
- 包围球半径修正：box 用 `hypot(ax, ay, az)`（外接球），不再用三条半轴长度相加（会高估 60%）。
- 坐标修正：
  - `origin` = 根节点的 ECEF 中心，内层 `group.position = -origin`（消除大坐标浮点抖动）；
  - `upFix` = `rotateX(-90°)` 作用在外层 `world` 上（Z-up → Y-up 整体转正）；
  - `centerRendered = (centerWorld - origin) · upFix`，保证 LOD 的距离计算和相机在同一坐标系。
- 加载调度：`MAX_PARALLEL = 8`、`MAX_LOADED = 900`，按投影像素从大到小排队（近处先清晰），
  LRU 淘汰并 dispose geometry / material。
