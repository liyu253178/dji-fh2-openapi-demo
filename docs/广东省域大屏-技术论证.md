# 广东省域态势大屏 · 技术论证

> 结论：**可行，建议做，工作量 3~4 天。**
> 关键前提是**不复用 sc-datav 的代码**（React + 省级装饰地图），而是用**纯 Vue 3 + three.js** 实现，
> 数据源已实测可用且坐标正确。详见下文的数据验证与风险项。
>
> 需求：单独做一页广东省域大屏，视觉形态参考 [sc-datav demo2](https://knight-l.github.io/sc-datav/#/demo2)，
> 行政区 geojson 自行获取。

## 一、需求理解与边界

| 项 | 结论 |
|---|---|
| 形态 | 独立页面（建议路由 `/screen`），**不改现有首页大屏** |
| 地域 | 广东省（21 个地级市） |
| 数据源 | 行政区边界 GeoJSON 自行获取；业务指标来自本平台已有接口 |
| 参考 | sc-datav demo2 的视觉语言（拉伸地块 + 描边发光 + 面板），**不抄代码** |

**明确不做**：不替换 `BaseMap`、不引入 React、不动现有大屏的坐标体系。
理由见 `sc-datav-大屏融合可行性分析.md`：省域装饰地图与真实瓦片地图互斥，混用会导致坐标不一致。

## 二、数据源验证（已实测，非推测）

### 2.1 可用源

| 源 | 结果 | 体积 | 说明 |
|---|---|---|---|
| **DataV.GeoAtlas**（阿里云） | ✅ HTTP 200 | 193 KB | `https://geo.datav.aliyun.com/areas_v3/bound/440000_full.json` |
| DataV.GeoAtlas（省界单要素） | ✅ HTTP 200 | 59 KB | `.../bound/440000.json`（只有省界，市界要用 `_full`） |
| geojson.cn | ❌ HTTP 301 | — | 不可直接用 |

**验证结果**：
- `FeatureCollection`，**21 个要素**（广州、深圳、东莞等 21 个地级市）✅
- 几何类型 `MultiPolygon`，数据完整可解析 ✅
- **坐标是真实经纬度**（非投影平面坐标）✅
  - 广州市范围 113.0~114.1 / 22.5~23.9 ✅
  - 极值点与权威值高度吻合：最南 20.2117（权威≈20.22）、最北 25.5168（权威≈25.52）、最西 109.6549（权威≈109.6）✅
- **坐标系为 WGS84**（GeoJSON 规范默认，DataV 官方说明亦为 WGS84）→ 叠高德底图**必须做 WGS84→GCJ-02 纠偏**

### 2.2 坐标系处理方案（已确认可行）

本项目已有现成工具 `web/src/utils/geo.js` 的 `wgs84ToGcj02()`，
与 `BaseMap` 用的是同一套纠偏逻辑 —— 边界与底图**可以精确对齐**，无需引入新库。

> ⚠️ 踩过的坑：不能用「行政几何质心 vs 已知地标坐标」判定坐标系
> （多边形质心偏离行政中心几十公里，会把结论带偏）。必须用**极值点**判定。

### 2.3 底图方案（二选一）

| 方案 | 说明 | 建议 |
|---|---|---|
| A. 纯装饰（sc-datav 做法） | 不用底图，行政区拉伸成块 + 材质贴图 | ✅ **推荐**。零外部依赖、内网可用、无坐标系风险 |
| B. 省域轮廓 + 高德底图叠加 | 真实瓦片打底 + 省界高亮描边 | 可行，但需纠偏对齐，且内网/离线环境瓦片不可用 |

**建议先做 A**。省域态势大屏的核心是「哪个市在飞、飞了多少」，拉伸地块足够表达，
且**没有底图就没有瓦片授权与内网问题**。若客户明确要真实地图，再做 B。

### 2.4 geojson 落地规格

| 项 | 实测值 | 处理 |
|---|---|---|
| 源文件 | `440000_full.json`，193 KB，21 要素 | 直接可用 |
| 坐标系 | WGS84 | 方案 A（纯装饰）**无需纠偏**；方案 B 必须纠偏 |
| 体积优化 | 193 KB 偏大 | 投影到平面坐标 + 限制小数位（6 位）后约可压到 80~120 KB |
| 精度 | 原始经纬度约 7 位小数（约 1cm） | 大屏按米级显示，保留 5 位足够 |
| 存放 | 建议 `web/src/assets/geo/440000.json` | 打进产物，内网可用 |

> 注意：`_full.json` 是「省界 + 21 个市界」（21 要素）；
> 不带 `_full` 的 `440000.json` 只有省界（1 要素），做地市高亮必须用 `_full`。

## 三、技术方案

### 3.1 技术栈（全部现有依赖，零新增）

| 层 | 选型 | 说明 |
|---|---|---|
| 框架 | Vue 3.5（`<script setup>`） | 与主应用一致，不引入 React |
| 3D | three 0.186（**已在项目里**） | 不需要 @react-three/fiber |
| 投影 | 手写墨卡托等距圆柱（**不需要 d3-geo**） | 经纬度 → 平面坐标只需几行，见下 |
| 图表 | ECharts 5.5（已在项目里） | 复用 `DashboardView` 的按需引入方式 |
| 指标数据 | 现有 `/api/ops/overview`、`/api/ticket/stats/*` | 不新增接口 |
| 自适应 | 现有 `clamp()` 方案 | 复用上一轮的做法 |

> 墨卡托投影（简化版）核心代码：
> ```js
> // 经纬度 → 平面（单位：米，相对原点），广东范围内误差 < 1m，足够大屏使用
> const R = 6378137;
> const x = R * (lng * Math.PI / 180);
> const y = R * Math.log(Math.tan(Math.PI / 4 + (lat * Math.PI / 180) / 2));
> ```
> sc-datav 用 d3-geo 是因为它要处理全球多投影，我们的场景**只要一个省内视角**，手写足够。

### 3.2 页面结构

```
web/src/views/GuangdongScreenView.vue
├── 顶部：标题 + 时间 + 全省汇总指标（今日架次/在飞/告警/本月里程）
├── 中央：three.js 画布
│   ├── 21 个地级市多边形（Shape → ExtrudeGeometry 拉伸成块）
│   ├── 顶面：微发光材质；侧面：暗色，营造立体感
│   ├── 在线/有任务的市：顶面高亮 + 呼吸光圈
│   └── 底部：模拟扫描光带（Plane + 渐变贴图，做 UV 偏移动画）
├── 左侧：各市飞行架次排行（ECharts 横向柱状）
├── 右侧：告警类型分布（饼/环）
└── 底部：近 7 天趋势（折线）
```

### 3.3 数据挂载（关键：只用真实数据）

| 大屏元素 | 数据来源 | 缺失时表现 |
|---|---|---|
| 各地市架次 | `/api/ops/overview` 的 `trend` + `flight.byStatus` 聚合 | 显示 0，不编造 |
| 在飞机场 | `/api/ops/snapshot` 的 `airports[].online` | 无在线机场 → 全市均灰 |
| 告警分布 | `/api/ops/overview` 的 `resources.alerts` | 为 0 时环图显示空态 |
| 工单分布 | `/api/tickets/stats/by-region` | 无数据时空态 |

> 接口路径注意：是 **`/api/tickets/...`（复数）**，不是 `/api/ticket/...`。

> **原则延续上一轮：宁可空着，不造假数据。**
> 地市高亮只按「该市有在线机场 / 有任务」判定，不用随机数模拟。

#### ⚠️ 已验证的一个坑：行政区粒度不匹配

实测 `GET /api/tickets/stats/by-region` 的真实返回：

```json
[{ "region": "广州市黄埔区穗东街道", "count": 3 }]
```

返回的是**街道级名称**（来自逆地理地址解析），**不是地级市名**。
直接拿去和 geojson 的 21 个地市做 join 会**全部落空**。

**对策**（三选一，需在开工时定）：

| 方案 | 做法 | 成本 | 准确度 |
|---|---|---|---|
| A. 前端做名称包含匹配 | `region` 字符串里是否含「广州」等市名 | 0.5 人日 | 高（覆盖 99% 场景，街道名必含市名） |
| B. 后端出地市口径 | 逆地理解析时增加 `city` 字段并存库 | 1 人日 + 存量数据需回填 | 最高 |
| C. 只用 ops 数据 | 放弃工单地域分布，改用飞行/告警指标 | 0 | 中（少了工单维度） |

**建议 A 先上**（成本最低且够用），B 作为后续优化。

#### 另一个口径问题

`/api/ops/overview` 的 `flight` 取的是**当期**数据（当前实测全 0，
而本地 `flight_task` 库里 9/28、9/29 有两条成功任务）。
大屏需要明确「今日/本月」口径，并与客户对齐「架次是否含历史任务与自动任务」，
否则领导看到的数字和业务台账对不上，会引发信任问题。

## 八、可行性实测（已跑通，非纸面推演）

geojson 已落地到 `web/src/assets/geo/440000.json`，并对渲染路径做了实测：

| 指标 | 实测值 | 结论 |
|---|---|---|
| 地市要素 | **21** | 广东 21 个地级市齐全 ✅ |
| 可拉伸多边形（外环） | **94** | 含海岛等离岛，Shape 全部合法，无退化环 ✅ |
| 边界顶点数 | **8183** | 数据精度足够，体积可控 |
| 预计三角形量 | **约 74K** | 单 draw call 量级，**性能无压力** ✅ |
| 平面跨度 | **839 × 641 km** | 与广东实际约 800 × 580 km 吻合 ✅ |
| 投影后体积 | 188 KB → **113 KB** | 可直接打进前端产物，内网可用 ✅ |
| 拉伸深度建议 | 6~10（km 坐标） | 足够呈现立体感 |

**结论：技术路径已验证成立**，21 个地市用 `THREE.Shape` + `ExtrudeGeometry` 拉伸渲染
在性能和实现上都不存在障碍。剩下的都是 UI 与数据对接的常规工作。

- 数据源**已实测可用**：DataV.GeoAtlas 广东省 21 市，WGS84 经纬度，已落地为 113KB 平面坐标文件
- 渲染路径**已实测可行**：94 个多边形 / 74K 三角形，无性能压力

- 工期 **4 人日**（含行政区名称 join）

**开工前需要客户确认两件事**（不确认会导致返工）：

1. **是否接受无底图的装饰地图**（方案 A）？若要真实高德底图（方案 B），
   需额外确认：①内网能否访问瓦片服务 ②是否接受 WGS84→GCJ-02 纠偏后约 500m 的偏移

   需与业务台账口径一致，否则大屏数字和台账对不上会引发信任问题。

**另需注意**：`/api/tickets/stats/by-region` 返回的是**街道级**名称，
需按 §3.3 的方案做名称匹配才能落到地市。
