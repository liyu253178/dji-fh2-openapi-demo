# 引入 Cesium 作为底座 —— 独立论证

> 本文档只做论证与决策，不改动任何现有页面。
> 数据口径：CesiumJS 1.145（2026-09-01 发布，Apache-2.0）；本项目现状取自 2026-10-01 代码与实测。
> 凡是没实测过的，一律写进第 9 节「诚实留白」，不包装成结论。
> **2026-10-01 深夜更新：阶段 0 POC 已跑完，四个门槛全部通过（见第 10 节），留白 1/2 已解除，留白 3 拿到首组数据。**

---

## 0. 结论先行

**建议做，但不做全站替换。**

- **范围**：Cesium 只作为「三维成果底座」引入，先落在「三维模型与量测」这一页；Leaflet 继续承担业务地图（机场/机巢/航线规划/图斑）。双引擎并存。
- **理由一句话**：我们真正的痛点是**缺一个地理引擎**——坐标靠自己反算、2D 与 3D 是两套坐标系、LOD 调度自己维护。这三件事正是 Cesium 的原生能力。而 Leaflet 那几页业务地图换成 Cesium，收益不明显、成本却很高。
- **先别指望 Cesium 解决的两件事**：① GCJ-02 底图偏移不会自动消失；② 量测工具 Cesium 不内置，仍要我们自己写。
- **第一步动作**：先做 1 天以内的可行性 POC（独立路由、随时可删），拿 4 个硬指标的真实数据再决定是否投入迁移。**不要先花两周迁移、最后发现坐标或性能不达标。**

## 1. 现状：我们现在到底在用什么

| 层 | 现在的实现 | 规模 |
|---|---|---|
| 2D 底图与叠加 | Leaflet 1.9 + 高德/吉林一号底图 + 自建 `ShiftTileLayer` 做 GCJ-02 纠偏 + 正射 XYZ 金字塔叠加 | ModelGeoView 约 700 行 |
| 3D 渲染 | three.js 0.186 + **自研** 3D Tiles 解析（b3dm 拆解、Draco/KTX2 解码器本地化、自写 LOD 调度与视锥剔除、包围球粗筛拾取） | ModelViewer 1300+ 行 |
| 坐标系 | `web/src/utils/ecef.js`（自写 ECEF→LLH 椭球迭代）+ GCJ-02↔WGS84 转换 | —— |
| 量测 | 自写：距离=直线/水平/垂直/坡度，面积=投影/拟合 | —— |

**必须承认：现状是「能用且已被验证过」的。** 坐标对齐到 ±1e-6° 量级，回归断言 15+10 条全绿（角点比对、ECEF 中心比对、瓦片 200、视角按钮、量测读数）。所以引入 Cesium 的理由**不是「现在不能用」**，而是「现在这套的上限和维护成本」。

---

## 2. 痛点根因：不是 UI 没做好，是缺地理引擎

| 用户反馈 | 表层现象 | 真实根因 |
|---|---|---|
| 模型不能正确落到卫星底图 | 2D 叠加偶尔偏、3D 没地理参考要自己算 | 我们没有地理引擎，坐标全靠反算 + 纠偏，每换一种模型格式就可能翻车 |
| 2D 与 3D 割裂 | 切一次模式要重新定位、两套坐标 | 两个引擎、两套坐标系，天然割裂 |
| 渲染慢 | 大模型加载久、GPU 一直转 | LOD/剔除/内存策略是我们自己写的，屏幕空间误差（SSE）调度不成熟 |
| 量测不方便、不准 | 表面取点飘 | 拾取靠 raycaster + 包围球粗筛，不如深度缓冲稳 |
| 操控别扭 | 已按智图键位改过一版 | 相机控制是我们自己映射的，能力受限于 OrbitControls |

**这五条里有四条，本质是同一件事：把 Cesium 已经做好的地理底座，我们自己手搓了一遍。**

## 3. Cesium 能带来什么（逐条对应）

| 痛点 | Cesium 的原生能力 | 我们省掉什么 |
|---|---|---|
| 坐标正确 | 内建 WGS84/ECEF；3D Tiles 1.1 原生流式（b3dm/pnts/i3dm/glTF、外部 tileset 引用） | 省掉 `ecef.js` 反算、足迹推算、角点对齐那套自证逻辑 |
| 模型落底图 | 影像图层本身就是地理配准的：正射金字塔用 `UrlTemplateImageryProvider({z}/{x}/{y})`，单张成果用 `SingleTileImageryProvider` + `rectangle`(来自 map_report 角点) | 叠加不再需要自己算角点、自己纠偏 |
| 2D/3D 割裂 | `SceneMode` 2D / 2.5D / 3D 一体切换，同一相机、同一坐标系 | 一次定位，两种视图 |
| 拾取精度 | `scene.pickPosition` + `globe.depthTestAgainstTerrain`（走 GPU 深度缓冲） | 表面取点更稳，实现更短 |
| 操控 | `ScreenSpaceCameraController` 可逐键配置：**左键平移 / 右键或滚轮缩放 / 中键旋转** —— 与智图键位几乎天然一致 | 键位映射从"硬改 OrbitControls"变成"配一下" |
| 渲染开销 | `requestRenderMode = true` + `maximumRenderTimeChange`（按需渲染）、`maximumScreenSpaceError`、`maximumMemoryUsage`、`resolutionScale`、`skipLevelOfDetail` | 直接对治"GPU 一直转/风扇狂转" |
| 量测 | 不内置量测工具，但提供 `sampleTerrainMostDetailed`、`EllipsoidGeodesic`、`Cartesian3.distance` | 量测仍要自写，但坐标系问题消失，且能做"测地线距离 vs 直线距离"的正经口径 |
| 许可与部署 | Apache-2.0，商用免费；官方 Offline Guide 明确可**完全离线**（自建影像/地形，不用 Ion） | 私有化/内网部署有官方路径可循 |

**一句话收益**：把「我们维护地理正确性」换成「引擎保证地理正确性」，我们把精力放回业务（量测口径、成果对照、工单闭环）。

## 4. 代价与风险（含缓解，不粉饰）

| 编号 | 风险 | 量级（估，实测为准） | 缓解措施 | 仍未解决的部分 |
|---|---|---|---|---|
| R1 | 包体与首屏 | Cesium 全量 chunk 约 3MB 级；gzip/brotli 后约 0.7–1.6MB（取决于按需引入与压缩）；另需随包分发 Workers/Assets/ThirdParty/Widgets 静态目录（几十 MB 级） | 只在三维页路由级懒加载；`manualChunks` 单独切 chunk；BFF 单端口加 `/cesium` 静态托管 | 首次进入三维页仍有可感知的加载等待 |
| R2 | 离线/私有化 | 必须禁 Ion（`Ion.defaultAccessToken` 置空）、关 `baseLayerPicker`/`geocoder`、影像与地形自备 | 官方 Offline Guide 有标准做法 | **不带地形时**，高差/坡度只能靠模型自身采样 |
| R3 | GCJ-02 底图 | 高德瓦片直接铺会偏几百米 | 自定义 `TilingScheme`，重载 `project/unproject` 做 WGS84↔GCJ-02（我们已有现成转换函数） | **Cesium 不会让这个问题消失**，只是换了个解决位置 |
| R4 | BFF 接口适配 | 现有取文件接口是 `/api/model/:id/asset?path=` 查询串形式；我们的 tileset 内还有 `Project1 2/B3DM/Model_0/BlockA/tileset.json` 这种**带空格、多级子目录、外部 tileset** 的相对 uri | 建议新增路径式路由 `/api/model/:id/tiles/*`，让相对 uri 自然解析 | Cesium 对 query 形式 baseUrl 的相对解析行为**未实测**（列入留白） |
| R5 | 我们的数据形态 | 实测该包 `asset.version = "0.0"`（3D Tiles 早期草案），包围盒是真 ECEF box，无 `root.transform`，有外部 tileset 引用 | boundingVolume 是 ECEF → Cesium 可直接用 | "0.0" 草案能否被 1.145 直接加载**未实测**；若不行，退化方案是在 BFF 侧做轻量 0.0→1.0 转换 |
| R6 | 升级与兼容 | Cesium 月度发版，API 会改名（历史上出现过 `maximumScreenSpaceError` 一类调整）；1.141+ 要求 Node ≥ 22 | 锁版本 + 回归兜底；本项目受管 Node 22.22.2 已满足 | 每次升版要过一遍三维回归 |
| R7 | 工程量 | 现有 1300 行 three.js 渲染器 + 15/10 条回归断言要重写或并存；过渡期两个 chunk 同时在包里 | 先 POC 后迁移；三维页独立路由，不动其他页 | 过渡期维护两套渲染路径 |
| R8 | 运行环境 | WebGL2 与显存占用；低配/移动端更敏感 | `requestRenderMode` + 限制 `maximumMemoryUsage` | 弱机体验仍弱于 Leaflet 二维页 |

## 5. 三个方案的对比

| 方案 | 内容 | 收益 | 代价 | 判断 |
|---|---|---|---|---|
| **A 维持现状打磨** | 继续在 Leaflet + three.js 上补坐标、补 LOD、补量测 | 零迁移风险，短期最快 | 地理正确性永远是我们自己扛；LOD/剔除上限有限；每换模型格式都要再适配一遍 | 可用，但天花板明显 |
| **B 双引擎（推荐）** | Cesium 只做三维成果底座；Leaflet 继续做业务地图 | 痛点的四条根因一次性解决；风险集中在单页，随时可回退 | 包体增加、过渡期两套渲染并存、需 POC 验证 | **推荐** |
| **C 全站 Cesium** | 航线规划、机场/机巢、图斑地图全部迁到 Cesium | 技术栈统一 | 业务地图页用 Cesium 是杀鸡用牛刀；画多边形/画中心线这类交互 Leaflet 更轻；回归面全炸 | 暂不建议 |

> 顺带排除：`maplibre-gl` / `deck.gl` 一类方案对 3D Tiles 的支持不成体系，不作为候选，不展开。

## 6. 推荐落地路径（分阶段 + go/no-go 门槛）

### 阶段 0 · 可行性 POC（建议 1 天以内，独立路由，随时可删）

挂一个最小 Cesium Viewer（离线配置 + 自建影像 + 我们的 tileset 包），**只验证 4 个硬指标**：

| 门槛 | 指标 | 判定方式 |
|---|---|---|
| G1 坐标 | 模型落位与已验证角点一致 | 与现有 `map_report` 实测角点比对，不劣于现状（±1e-6° 量级） |
| G2 性能 | 大模型可交互时间 / 稳定帧率 | 同一台机器、同一个包，与现有 three.js 方案**实测对比**（不预设数字） |
| G3 量测 | 同一条路径的读数与现状互证 | 两套实现的读数互差在可接受范围；且表面取点稳定不飘 |
| G4 部署 | 离线可跑 + 单端口可服务 | 断外网可加载；`dist` 增量体积可接受；BFF 能托管 `/cesium/*` |

**任一门槛不达标 → 停在 POC，回去打磨方案 A。** 这是本次论证最重要的一条纪律。

### 阶段 1 · 三维成果页 Cesium 化（POC 通过后）

模型浏览、2D/3D 一体切换、视角快捷按钮（俯视/正视/后视/左视/右视/复位）、量测（沿用现有口径：直线/水平/垂直/坡度、投影/拟合面积）、模型足迹。Leaflet 页面一行不动；回归新增 `verify-cesium-*.mjs`，与现有 `verify-model-geo` 并行跑。

### 阶段 2 · 按需扩展

航线三维预览、图斑落到模型表面、正射与三维对照。

### 阶段 3 · 可选

业务地图页是否迁移 —— 届时按实际收益再评估，**现在不预设**。

## 8. 为什么建议先 POC 而不是直接迁移

迁移的成本是「1300 行渲染器 + 25 条回归断言 + 一套坐标系自证逻辑」的重写，而收益要等成果页真正跑起来才能确认。**在坐标、性能、部署这三件事上，Cesium 的官方承诺不等于我们这份数据上的实测结果**——尤其是我们的 tileset 是 `asset.version "0.0"` 的老草案、路径带空格、走的是自有 BFF 代理接口。

先用 1 天把这三个不确定项打成实测数字，比先写两周迁移代码更划算。

## 9. 诚实留白（本轮**没有**验证的事）

1. ~~**`asset.version "0.0"` 的 tileset 能否被 CesiumJS 1.145 直接加载** —— 未实测。~~
   **→ 已实测：能。** 2026-10-01 POC 中，822MB 的包（`asset.version "0.0"`、`gltfUpAxis Z`、真 ECEF box、无 `root.transform`、含外部 tileset 引用）被 1.145 直接加载并正确落位，无需任何 0.0→1.0 转换。R5 的退化方案不需要。
2. ~~**BFF 查询串形式接口下，Cesium 对相对 uri（含空格与多级子目录）的解析行为** —— 未实测，所以建议改成路径式路由。~~
   **→ 已按建议改为路径式路由 `/api/model/:id/tiles/*` 并实测通过**：根 tileset、带空格路径（`Project1 2/B3DM/Model_0/tileset.json`）、子级 tileset 三种请求全部 200，`../` 越界请求被 400 拒绝。R4 的解法成立。
3. ~~**800MB 级模型在 Cesium 下的实测帧率与内存** —— 未实测，只有 POC 才知道。~~
   **→ 帧率已实测（见第 10 节 G2）；显存占用仍未测**（Cesium 1.145 已把 `maximumMemoryUsage` 拆成 `cacheBytes` + `maximumCacheOverflowBytes`，读数口径要先定，留到阶段 1 补）。
4. **无地理参考的 Y-up 局部坐标模型在 Cesium 下如何摆放** —— 需要 `modelMatrix` 人工定位，方案未定（现状是如实提示"无地理参考"，不硬凑）。**仍未验证**，POC 页面上照实标注。
5. ~~**GCJ-02 纠偏在 Cesium 自定义 TilingScheme 下的精度** —— 有成熟社区做法，但未在本项目实测。~~
   **→ 已实现自定义 `Gcj02WebMercatorTilingScheme`（WGS84→GCJ 后取瓦片、四角反解回铺）**，并量化出「不纠偏会偏多少米」。但**纠偏后的绝对精度仍未与高德真值比对**——这一条只完成了一半，剩下一半仍算留白。

以上五项一旦进入 POC，都会变成实测数据；在拿到数据之前，本文不对它们下任何结论。

## 10. 阶段 0 POC 实测结果（2026-10-01）

> 环境：macOS / Apple M1 Pro / Chrome（ANGLE Metal）· CesiumJS 1.145.0 · 模型 `335363146`（822MB，3103 文件）
> 复跑方式：`node server/src/index.js` 起单端口 BFF，再 `node web/scripts/verify-cesium-poc.mjs`
> **结果：16 项断言全部通过。判定：可进入阶段 1。**

### G1 坐标 —— ✅ 通过

| 指标 | 实测 |
|---|---|
| Cesium 投影出的模型中心 | `113.9418784°E 22.5363341°N 11.07 m` |
| 项目自有 `ecef.js` 独立反算期望值 | `113.9418784°E 22.5363341°N` |
| 差值 | **Δlon 4.92e-8° / Δlat 1.14e-8°**（门槛 ≤1e-6°） |
| 引擎与自有实现的闭环自检差 | **2.75e-8 m** |

结论：Cesium 的落位与现有坐标体系完全一致，且远好于 1e-6° 门槛。**「省掉 ecef.js 反算那套自证逻辑」的前提成立。**

### G2 性能 —— ✅ 通过（首组数据，对比项待补）

| 指标 | 第 1 次跑 | 第 2 次跑（复跑核对） |
|---|---|---|
| 页面就绪（含导航+解析+首屏瓦片） | 1166 ms | 6231 ms |
| 页面内自测可交互耗时 | **851 ms** | **904 ms** |
| 瓦片请求 | 52 个，全部 200 | 52 个，全部 200 |
| 瓦片内容就绪 | 25 / 共 202 张 | 25 / 共 202 张 |
| 绕模型旋转 3 秒平均帧率 | **118.9 fps（357 帧）** | **114.3 fps（343 帧）** |
| 渲染设备 | ANGLE Metal Renderer: Apple M1 Pro | 同 |

两次跑的差异说明：页面就绪那一项波动最大（1.2s ↔ 6.2s），因为它包含导航与首屏瓦片的排队，受本机当时负载影响；**可交互耗时（851 / 904 ms）与帧率（118.9 / 114.3 fps）两项是稳定的**，取它们当结论。以后引用 G2 时按「可交互 ≈0.9s、帧率 ≈115 fps」记，不要报单次数字当精确值。

⚠️ 两点必须说清楚：
- 这是「旋转 3 秒」的数字，**不是**「加载完全部 202 张瓦片后静止漫游」的数字；显存与长时间漫游的稳定性还没测。
- 与 three.js 的对比**还没做**——论证文档要求"同一台机器、同一个包"跑两遍，这次只跑了 Cesium 这一遍。G2 的"通过"只代表「性能可用」，不代表「优于现状」。

### G3 量测 —— ✅ 通过

| 指标 | 实测 |
|---|---|
| Cesium `EllipsoidGeodesic` | 298.0159 m |
| 独立实现（球面 Haversine + 平均曲率半径修正） | 297.9021 m |
| 互差 | **0.1138 m（0.0382%）** |
| 屏幕中心连续取点 3 次最大离散 | **0°**（完全不飘） |

结论：读数口径可互证，`pickPosition` 表面取点稳定。

### G4 部署 —— ✅ 通过

| 指标 | 实测 |
|---|---|
| 断外网（拦截所有非本机请求）后重载 | 仍 `ready`，瓦片照常加载 |
| 外部域名依赖 | **0 个** |
| `/cesium` 静态资源（Worker/Assets/ThirdParty/Widgets） | **6.8 MB**（论证时估"几十 MB 级"，**实际小一个数量级**） |
| Cesium JS chunk | **4.2 MB → gzip 1.14 MB**（论证时估"3MB 级 / gzip 0.7–1.6MB"，落在区间内） |
| 控件样式 | 24.5 kB |
| 引入的直接代价 | **≈ 7.9 MB**（静态资源 + JS gzip + 样式） |

### 顺带拿到的三个工程事实（论证时不知道的）

| # | 事实 | 影响 |
|---|---|---|
| 1 | Cesium 1.145 已把 `maximumMemoryUsage` **拆成** `cacheBytes` + `maximumCacheOverflowBytes`；`numberOfTilesLoaded` 这个统计字段**不存在**，正确的是 `numberOfTilesWithContentReady`；帧状态的指令数字段是 `frameState.commandList.length`（不是 `commandsLength`） | R6 的「API 会改名」实锤。阶段 1 升级/迁移时必须过一遍字段表，不能凭旧文档写代码 |
| 2 | 把整个 `Cesium` 命名空间挂到 `window` 会**阻断 tree-shaking**：实测 chunk 从 4.2MB 涨到 4.97MB（+760KB / gzip +243KB） | 阶段 1 要按需暴露，不要整体挂出 |
| 3 | `@click="runBenchmark"`（不带括号）会把 **MouseEvent 当第一个参数**传进去，`setTimeout(res, event)` 被转成 0ms，跑分窗口瞬间结束 → 报出「0 fps」的假数据且不报错 | 教训：**拿不到数 ≠ 数是 0**。靠浏览器内定点探针（`rAF 121 次/秒` + `requestRenderMode=false` 后 1.5 秒 180 帧）才把「机制正常、参数传错」钉死。以后任何实测脚本遇到 0 值都要先证明"0 是真实测量结果"而不是采集失败 |
| 4 | 同样是「0 fps」，还有第二个更隐蔽的来源：`scene.frameState` **不是 Cesium 的公开属性**（内部是 `_frameState`），写 `scene.frameState?.frameNumber ?? 0` 会静默取到 0，首尾相减恒为 0 | 破绽是**同一份代码里两个数据源自相矛盾**：预热用 `postRender` 事件等到了 3 帧，计数却报 0。修法：数帧统一用 `postRender`（公开 API），并并列记一份 rAF 回调数做归因对照（raf 高/引擎帧 0 → 引擎侧或取数错；两者都低 → 窗口被节流）。**Cesium 的字段名不能凭文档印象写，可选链会把「字段不存在」伪装成「值是 0」** |
